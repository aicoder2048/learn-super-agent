事件驱动（下）：上下文组织与提前行动

事件过滤、路由之后，它进入了目标会话。接下来有两个问题：往模型的上下文里放多少信息？能不能在人开口之前就把活干了？原文分别用 Cache 和 CPU 投机执行的思路回答。

学完本课，你能够：

  • 解释为什么原文说“浪费上下文窗口，就是浪费模型的智能”。
  • 说出 Inline & Spill 的含义，并按原文三步决定一条事件该注入什么。
  • 用链式召回演示 Router 如何沿 ID 一跳一跳找回旧任务的上下文。
  • 说明投机执行用什么换什么，以及“静默复现并修复”策略为什么默认保持安静。

01该注入多少上下文

先说结论：注入太多和太少都有代价。要找的是中间那个点。

在单 Session Agent 里，输入主要是人写的提示词，数量有限。在 Super-agent 里，输入换成了环境持续产生的半结构化事件（Trigger）。所以，工具调用和事件注入的结构设计变得更重要。

注入过多

挤占窗口，稀释模型注意力。

无关的历史和别的任务的细节，会把真正要看的信息淹没。

注入过少

模型被迫反复调用工具去读。

每一次读取都是一次往返，执行步数增加，响应变慢。

浪费上下文窗口，就是浪费模型的智能。§3.3

原文的解法是：把有限的上下文窗口当作 Cache 来管理。

02Inline 与 Spill

原文借用编译优化和计算机系统的概念，把上下文注入归纳为两个基本操作。

操作一
Inline（内联）

把近期很可能用到的信息，直接放进当前上下文窗口。好处：省去一次额外的工具调用往返。

操作二
Spill（溢出）

超出窗口预算或低频使用的完整信息，留在窗口之外。窗口里只保留引用或摘要，模型需要时再按需读取。

决定“近期很可能用到什么”的依据，是经典的局部性（Locality）思想：和当前对象紧密关联的、时间或空间上相邻的信息，最可能马上被用到。

补充：这几个词从哪来 Cache 与局部性：CPU 缓存只存一小部分数据，却能命中大部分访问，靠的就是“刚用过的和挨着的，接下来还会用”。
Inline：编译器把一个小函数的函数体直接抄进调用处，省掉一次函数调用的开销。对应这里“省掉一次工具调用往返”。
Spill：寄存器不够用时，编译器把变量“溢出”到内存，只在需要时再读回来。对应这里“完整内容留在窗口外，保留续读入口”。
这些类比是课程作者的解释；原文只说“借用编译优化与计算机系统中的概念”。

03三步注入法（动手）

原文给出了用 Inline & Spill 逐步优化事件注入的三步。

  1. 从最少信息开始：最初只提供当前对象的 ID 和内容摘要。
  2. 利用局部性逐步 Inline 关联信息：先附上紧密关联对象的 ID，再附带时空相邻的内容。例如：内容前 50 字、IM 消息的前后相邻消息与所回复的消息，或代码评论所在评审讨论中的相邻评论。
  3. 超出上限则 Spill：对无法全部 Inline 的长内容设定较小的长度上限，把超出部分 Spill 到窗口外。一种简单直接的做法是：截断超出部分，并保留续读入口。模型需要完整内容时，再调用工具读取。

下面的演示里，群聊中有人发来一条新消息，系统要把它注入一个 Worker 的上下文。拖动“上下文预算”，看三步法如何决定哪些信息进窗口。

演示：一条 IM 消息该注入什么？
Trigger #42 · 群聊「登录服务」· 张三 · 回复 #39@agent 上次那个登录超时的修复，顺便把重试次数改成 3 吧，日志里我看还是会偶发失败……（后面还贴了 380 字的报错日志）
候选信息按原文三步的优先级排列。★ 表示完成这条请求真正需要的信息。
    注入字数（占预算）
    从 20 字往上拖。预算太小时，只有 ID 和摘要进窗口，需要的信息都要靠工具去读，额外调用多。预算适中时，紧密关联的信息被内联，长内容被截断并留下续读入口，调用数降到很低。预算拉满时，连整段 Thread 历史都塞了进来：调用数不再减少，无关字数却猛增，这就是“稀释注意力”。
    简化模型：按优先级贪心放入；可截断的长内容最多截到 50 字（Spill），其余放不下就只留引用。每缺一条 ★ 信息、或 ★ 信息被截断，记 1 次额外工具调用。字数是示意值，不是原文数据。
    看演示要点三步法的顺序本身就是一种 Cache 替换策略：越可能用到的越先放；放不下的长内容不是丢掉，而是“截断 + 留续读入口”。模型从不会因为信息被 Spill 而失去它，只是要多付一次读取。

    04链式召回

    系统长期运行后，会积累大量历史任务。而且，大量后续事件已经通过订阅与直通直接发给 Worker，不经过 Router。这给 Router 层带来一个两难：

    • 它不能把所有任务的全量历史都放进自己的上下文窗口；
    • 它又需要在用户跨信道提起某个旧任务时，找回当时的上下文。

    原文的回答是：把 Inline & Spill 一致地应用到系统中的各类对象上。这样就自然得到一种按需展开的多跳检索机制——链式召回（Chain of Recall）。

    机制系统为 Trigger、Thread 和 Worker Session 等对象赋予唯一 ID，并在注入时内联紧密关联对象的 ID，使这些对象在底层构成一张引用图。每次召回的对象本身也遵循 Inline & Spill，返回结果中又内联下一跳关联对象的摘要与 ID。

    原文的例子：从一条当前消息读取所在 Thread，再从 Thread 内联的 ID 追踪到相关的 Worker Session，进而找到该 Worker 关联的另一个代码评审 Thread。下面的演示把这个过程做成可以点的。

    演示：用户在 IM 里问起一个旧任务
    Trigger #57 · 群聊「数据导出」· 李四之前那个导出 CSV 中文乱码的问题，PR 合了没？
    点亮的方框是“已读到”的对象，虚线框是“当前上下文里已有它的 ID、可以读”的下一跳。灰掉的方框，Router 现在还不知道它存在。顺着 ID 点下去，看 Router 用几跳就能回答问题。
    示例对象和内容是虚构的，结构依照原文图 8 与 §3.3 的描述。
    链式召回的关键没有一个“中心索引”。线索就分散在每个对象里：每个对象都内联了邻居的 ID 和摘要。模型拿着当前事件，像顺藤摸瓜一样往外走，需要几跳就走几跳。原文说，这缓解了 Router 层在长程运行中丢失先前信息的问题。
    局限链式召回主要解决近期任务与会话历史的按需检索。原文在 §8.1 承认：运行周期拉长到跨月甚至更长时，长程记忆会成为可扩展性的主要瓶颈。见 SA09。

    05提前行动：投机执行

    前面几节讲的是“事件来了怎么处理”。这一节讲：能不能在人还没下指令时，就先动手？

    原文思路借鉴计算机系统中的投机执行（Speculative Execution）思想：Agent 可以在还不确定结果是否会被采用时，根据环境信号在后台提前尝试，通过消耗额外的后台算力来减少人类的等待与介入成本。结果有价值就交付，没有价值就丢弃。

    原文给了两个场景：

    个人助手场景
    会议邀约

    收到会议邀约邮件或待办消息时，Agent 先在后台核对日程冲突、搜集相关背景资料、备好回复草稿。用户过目后直接确认发出。

    研发协作场景
    静默复现并修复

    原文在 DeepSeek Harness 内部用户群里配置了这条策略：群里有人反馈问题或讨论改动方案时，Agent 先在后台尝试复现、寻找修复方案。只有确认问题并找到简单修复方案后，才把结果交付给用户；否则全程保持安静。

    演示：投机执行用什么换什么
    关掉“投机执行”，对比同一件事的时间线。开启时，Agent 用后台算力去“赌”一次；赌中了，人等待的时间大幅缩短；赌不中，结果被丢弃，群里一条消息都不多。
    简化模型：时间单位是分钟，数值是示意。关闭投机执行时，假设讨论结束后有人 @agent，Agent 再开始同样的工作。
    补充：CPU 里的投机执行CPU 遇到条件分支时，不等条件算出来，就先猜一个方向往下执行。猜对了，结果直接用，省下等待；猜错了，把算出来的结果全部丢弃，从正确的分支重来。代价是做了一些“白干”的计算。Super-agent 的版本完全同构：用后台算力换人的等待，猜错就丢弃，不能让错误的结果“泄露”出去——对应到这里，就是不发出无用的消息。
    常见误解投机执行不是“想到什么就往群里发什么”。“静默复现并修复”的精髓在于交付门槛：确认问题、修复简单，两条都满足才说话。它和 SA01 讲的“主动 = 做值得做的事 + 没事保持安静”是一回事。这条策略本身是写在语义层里的（见 SA03 的两级过滤）。

    06自测与速记

    原文对“Spill”的一种简单直接的做法是？
    原文 §3.3 第 3 步：对无法全部 Inline 的长内容设定较小的长度上限，截断超出部分并保留续读入口。
    按原文的三步法，下面哪一项最适合在第 2 步“利用局部性逐步 Inline”时加入？
    原文举例：内容前 50 字、IM 消息的前后相邻消息与所回复的消息、代码评论所在评审讨论中的相邻评论。它们在时间或空间上相邻，最可能马上用到。
    链式召回能够“一跳一跳”展开，关键原因是？
    对象靠唯一 ID 构成引用图；每个召回结果都内联下一跳的 ID 与摘要，模型就能顺着引用关系按需展开。
    在“静默复现并修复”策略下，Agent 后台复现了问题，但发现修复需要团队做设计取舍。按原文的描述，它应该？
    原文：只有在确认问题并找到简单的修复方案后，才会把结果交付给用户，否则全程保持安静。投机执行的结果“没有价值就丢弃”。

    速记表

    要点一句话
    核心矛盾注入过多稀释注意力，注入过少反复调工具；浪费窗口 = 浪费智能
    视角把上下文窗口当 Cache 管理
    Inline近期可能用到的信息直接放进窗口，省一次往返
    Spill超预算或低频的完整信息留在窗口外，只留引用/摘要；截断 + 续读入口
    三步法最少信息（ID + 摘要）→ 按局部性 Inline（关联 ID、前 50 字、相邻/所回复消息）→ 超限 Spill
    链式召回对象有唯一 ID，内联邻居 ID，构成引用图；按需多跳展开；解决近期历史检索
    投机执行用后台算力换人的等待；有价值就交付，没价值就丢弃
    静默复现并修复后台复现 + 找修复；确认问题且修复简单才发声，否则全程安静
