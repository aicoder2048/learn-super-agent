开源原型 dsh-superagent 拆解

文章讲的是思路，原型是这条思路的一份公开代码。本课按原型文档的顺序拆解它，回答四个问题：

  1. 它用哪些概念？
  2. 它怎样决定接不接活？
  3. 它怎样执行和交付？
  4. 它和文章的设计差在哪里？
来源：dsh-superagent-prototype 的 README、SETUP 与 docs/000–007阅读约 25 分钟含 2 个互动演示

学完本课，你能够：

  • 说清原型的定位和边界：面向单个 GitHub 仓库的研究原型，不是正式产品。
  • 按顺序讲出一个请求的一生：Source → Trigger → Thread → Eval → Ticket/Mandate → Assignment → Executor → Channel。
  • 判断一条消息在 off / observe / auto 三种接受模式下，系统怎样处理它。
  • 解释“上下文不等于权限”：订阅送来的消息为什么不能扩大授权。
  • 对照文章的五个模块，指出原型做到了哪些、简化了哪些、文档没有提到哪些。

01原型是什么，不是什么

先说结论：dsh-superagent 是一个面向单个 GitHub 仓库的主动式编程 Agent。它以扩展包（bundle）的形式运行在 DeepSeek Harness 里，采用 MIT 许可。

它做什么
接请求 → 开工单 → 交付

它监听 GitHub，可选监听飞书。得到授权的人请它做事时，它开一个工作项。它在独立的 Session 和目录里干活，然后在原来的对话里回复，例如提交一个 Pull Request。一个网页面板显示需要人处理的事。

它不是什么
不是正式产品

README 第一段就声明：这是仅供参考的研究原型，不是 DeepSeek 的正式产品。代码可能有缺陷，风格可能不一致，用之前要审查和改造。

We have adapted it for publication, so it is not identical to our internal version or the implementation described in Exploring Super-agent Design. Some designs discussed in the article are directions for future development and are not implemented in this prototype.README

这句话的意思是：公开版经过改编，和团队内部版本不同，也和文章描述的实现不同。文章里的部分设计是未来方向，原型里没有。所以读这一课时，要分清三样东西：文章的设计、原型文档写明的行为、我们推断的东西。本课只讲前两样；没有文档支持的地方，会写“文档未提及”。

补充：原型的文档怎么读原型的文档按编号 000–008 排列。README 要求按顺序读：每篇只依赖前面已经介绍过的概念。本课的小节顺序也照这个来：000 哲学 → 001 领域模型 → 002 授权 → 003 执行 → 004 提示词 → 005 面板。

02设计哲学：为注意力而设计

原型的核心原则（000-philosophy）尽可能少地占用人的注意力，尽可能多地创造价值。

这条原则直接呼应文章的出发点。SA01 讲过：多任务的上限取决于人的注意力。原型把这个判断变成了一条评审标准。下面每一样都占用某人的注意力：消息、通知、问题、设置、面板元素、文档段落。它给出的价值必须大于这份成本，否则就删掉。

由此，原型给 Agent 定下五条行为准则：

  1. 只在有人请求、或团队写的规则允许时才行动。没人要的工作需要一条团队写的规则，而且先从“只记录不执行”的模式开始。
  2. 只在有人必须行动、或能用上结果时才说话。接到请求确认一次，干活时保持安静，有结果、需要决定或做不完时再开口。
  3. 一次只问一个具体问题，用结构化的方式问，免得问题埋在长报告里。
  4. 按影响决定停在哪里，而不是按工作量。局部改动做到可审查为止；需要设计决定的改动，带着清楚的问题停下。
  5. 诚实汇报。草稿标明未完成，失败就报失败，不绕过限制来避免提问。

对设计本身，原型也有对应的要求：

  • 概念少；
  • 设置少；
  • 面板只显示需要人处理的东西；
  • 文档按顺序读。
运营者的责任Agent 用团队每天都能看到的账号评论、提 PR、发消息。它发出的每条消息都消耗同事的注意力，责任在运营者。原型给了四条建议：从窄处开始（名单短，主动工作只记录）；调低噪音（Agent 太吵就把提示词改短、改严，或暂停它，不要再加消息解释噪音）；不要用它刷量；为它说的话负责。

03领域模型与请求的一生

原型只用少数几个领域概念。代码、Agent 调用的工具、面板和文档都只用这些词。下表列出核心概念，并对照文章里的说法。

原型概念定义（据 001-domain）对应文章的说法
Source一个事件流，如 GitHub、飞书。保存读取位置，重启不重放事件；丢掉机器人自己的消息工作信道
Trigger一个不可变的事件，带 Source 给的元数据（如发送者）。同一 Trigger 即使接受两次，也只建一个 TicketTrigger
Thread按时间排列的 Trigger；同一时间最多运行一个 EvalThread
Eval对一批 Trigger 的判断：gate（确定性准入）+ assessment（模型研判）→ Decision两级过滤 + Router 的分派判断
Mandate接单授予的权限：Policy 版本、范围、强度、匹配的规则、请求者身份。不可变文章未单独命名
Ticket一个已授权的工作单位，只有 Eval 能创建一个任务
AssignmentTicket 与一个 Executor 实例的绑定；一个 Ticket 可以先后有多个分派
Executor每个 Ticket 一个执行器 Session（代码里叫 worker）和一个目录Worker 层
主 Session评估 Trigger、接单、分派并回复的 Session（代码里叫 orchestrator）Router 层
SubscriptionTicket 与 Thread 的多对多关系。匹配的 Trigger 扇出（fan-out）给每个订阅的活跃 Ticket订阅与直通
ChannelThread 的“写”的一面：确认、回复、PR 都是写多信道交互的输出端

原型还列出了它拒绝的概念，这些拒绝同样有启发。例如：它不设“追加到工单”这种 Decision，因为追加就是订阅扇出，不需要 Eval；它不让 Correlation（线程之间的关联）参与路由，路由只靠订阅，关联只补充上下文；它不把“人”建成一个实体，人只是 Trigger 上的元数据，跨平台的身份对应写进提示词。

04授权：谁能下任务

先说结论：原型里，权限由宿主代码强制执行，不由消息内容决定。名单、规则和 Mandate 都由宿主检查。消息、评论和引用的文档只是判断的输入。它们改不了这些权限。

一条 Trigger 的两条路

路径一：Eval（决定要不要开新工作）

Source 先标记这条消息有没有找 Agent：mention 表示 @ 了 Agent，direct 表示私信。然后 gate 按发送者和这个 Source 的 Policy 检查：

  • 名单内的人找 Agent → 明确请求（explicit）。
  • 其他人的消息 → 查准入表。
  • 机器人名单里的机器人 → 最多是推断候选，永远不是明确请求。其他机器人不准入。

路径二：订阅（继续已有的工作）

Ticket 订阅了一个 Thread 后，这个 Thread 上的每条消息都作为上下文送给它，包括机器人和 CI 的消息。这条路绕过 gate，也不授予任何新权限。每个 Ticket 仍受自己的 Mandate 限制。

人在 Ticket 自己的 Thread 上跟进时，由这个 Ticket 的执行器决定怎么办。范围内就处理。超出范围或属于别的 Ticket，就交回去，重新走 Eval。

上下文不等于权限订阅的对话为任务提供信息，但不扩大任务的授权范围。要做更大范围的事，需要一次新的接单，生成新的 Ticket 和 Mandate。

接受模式与规则

接受模式只管推断出的工作，属于 Policy 的一部分：

模式效果（据 002-authorization）
off任何推断都不成为候选：没 @ 的消息、机器人消息、名单外人员的跟进
observe（默认）系统研判推断候选。研判为正面时，记为 ignore 并标记“本会接受”（would accept），不真正接单
auto推断候选研判为正面，就接单。主动接单至少要匹配一条已启用的规则

明确请求在三种模式下都有效。文档建议：先用 observe，看过记录下来的 Decision，再切到 auto。每条规则描述一种主动工作；Ticket 的 Mandate 记下匹配的规则，执行器会收到规则的名字和指令。

模拟：同一串消息，在不同模式下怎样处理
    切换模式和规则，看哪些消息会变成工单。重点看三条：
    • 第 3 条：名单内的人没 @，属于推断。
    • 第 4 条：机器人名单里的机器人，属于推断。
    • 第 7 条：订阅线程里，名单外的人追加要求。
    名单：alice、bob 在允许名单内；dependabot[bot] 在机器人名单内。假设这个群设为“全部消息”。规则以 002-authorization 为准。消息和规则内容是演示用的例子。研判结果做了简化：只看消息是否落在规则描述的范围内。
    Policy 改了，进行中的工单怎么办规则、接受模式和各 Source 的名单、准入表一起组成 Policy 版本，每个 Mandate 都记下它。版本变化时，系统丢弃正在运行的 Eval，并重新排队。受影响的活跃 Ticket 会收到一条通知。系统不立刻取消它们，因为取消会留下做了一半的工作。已结束的 Ticket 要恢复时，会按当前 Policy 重新校验 Mandate，校验不过就不能恢复。

    05执行、交付与恢复

    接单之后，工作交给执行器。下面按 003-execution 的顺序讲要点。

    每个 Ticket 一套
    Session + 目录

    执行器 Session 叫 worker-<ticket id>，目录以 Ticket 的短名命名。第一次派工前，准备命令（prepare command）运行一次，最多 10 分钟，典型做法是用 git worktree 建一份检出。

    不阻塞
    5 秒转后台

    执行器的预设把前台 shell 命令在 5 秒后转为后台任务。这样它在下一步就能收到新消息，而不用等长命令跑完。后台任务完成后，结果会唤醒执行器。每轮之后，后台工作最多再跑 30 分钟。

    并发
    工位（slot）+ 1 个人的专用位

    并发上限按工位计。额外留一个工位给人的消息或状态查询，所以新工作不会挡住人继续推进已有的 Ticket。CI 结果等其他输入要等普通工位。

    汇报
    结构化的 Report

    Report 有六种：progress、waiting、ready、blocked、failed、dropped。面板按它算出 Ticket 在等谁：等人回答、等人审查、受阻、排队、工作中……

    交付与合并

    结果回到原来的对话。聊天消息默认一句话，硬上限 100 词。GitHub 消息以一行声明开头，默认是 This is by an automated agent, not a human。

    合并的默认做法很保守。执行器从不以 Agent 账号开启自动合并。原因是 GitHub 会把合并记在开启的人名下。默认指令只允许满足以下全部条件的自动合并：

    • PR 是为这个 Ticket 开的；
    • PR 已就绪；
    • 所需审批覆盖最新提交；
    • 增删合计少于 200 行；
    • 使用另一个账号的 CLI。

    否则由人来合并。

    失败与恢复

    • 临时故障先重试。模型服务或网络出现临时错误时，执行器按递增的间隔重试三次。临时错误包括 HTTP 408、429、5xx，以及连接拒绝、重置或超时。
    • 先存再做。接单之后的每个动作，例如转发候选、派工、投递输入，都先存下来再执行。失败的投递从 2 秒开始退避重试，间隔翻倍，最长 1 分钟。
    • 重启后带恢复说明。重启时，正在运行的派工以“host restarted”结束。新派工带一条恢复说明：先检查目录、git 历史和 GitHub，再决定是否重复对外操作。
    • 人的暂停一直有效。人设置的暂停跨越跟进、新 Session 和重启，直到人解除。自动反馈从不恢复已暂停的工作。
    补充：对照文章“5 秒转后台、完成后唤醒”在效果上接近文章 §4.1 的异步 ReAct Loop：耗时命令不会卡住前台。但文档描述的是“shell 命令自动转后台任务”，没有使用文章里 start() / stop() 的说法。两者是否同一套机制，文档未提及。

    06提示词与监督面板

    团队能写什么

    团队可以编辑三个段落，并添加技能（skill）：

    段落写什么
    Communication（沟通方式）何时发消息；消息怎么写；GitHub 消息的开头一行；怎样处理评审；哪些普通账号其实是评审机器人
    Ticket scope（工单范围）Ticket 什么时候继续、什么时候带着草稿停下
    Delivery requirements（交付要求）PR 里要附哪些证据、自动合并的条件和行数阈值、提交作者
    Team skills（团队技能）Agent 需要时才加载的知识，例如一个 identities 技能，说明哪个飞书用户对应哪个 GitHub 账号

    改提示词，只改变模型读到的指令。它不改变 gate、Mandate、工具检查和账号包装器，这些由代码强制执行。文档给出了从强到弱的优先级：

    1. 工具和宿主强制的事实：身份、权限、工具参数检查、回复用途、长度上限。提示词改不了。
    2. 内置段落和生成段落（含团队对它们的覆盖）。
    3. 主动 Ticket 所匹配规则里的流程和沟通要求（只对这个 Ticket 的执行器有效）。
    4. 团队段落和团队技能。
    5. 外部文本：消息、评论、文档和引用。它们是数据，永远不改变规则或授权。

    提示词每次保存都生成一个不可变版本。Session 在每次模型请求时读取最新版本，所以改提示词不需要重启。

    面板回答三个问题

    面板位于 DeepSeek Harness 网页侧边栏的 Superagent 入口。打开它，依次回答：

    1. 现在有什么需要我？
    2. 系统健康吗，在做对的事吗？
    3. 某项工作从 Trigger 到 Eval 再到 Ticket 的完整历史是什么？

    页签按工作流排列：Overview、Source、Trigger、Eval、Execution、Settings。面板原则之一是“默认安静”：

    • 健康状态不占额外空间；
    • 问题必须可操作；
    • 一次性的网络错误不算问题。

    07与文章设计的对照

    下表把文章的五个模块逐一对到原型文档。已实现表示文档明确描述了对应机制；部分表示有相近机制但形式不同或范围更小；文档未提及表示原型文档里找不到对应描述，不代表内部版本没有。

    文章模块原型原型文档里的对应（出处）
    双层架构：Router + Worker（§2）已实现主 Session（orchestrator）只做路由，用较小的工具集，路由备注不超过 30 词；每个 Ticket 一个执行器 Session（worker）。（003、004）
    Router 批处理（§2.1）部分每个 Thread 的 Eval 串行运行，期间到达的 Trigger 合并成下一批；一次路由调用可以处理多个候选。（001、004）文章的批处理是在整个 Router Session 层面讨论的。
    两级过滤（§3.1）已实现Eval 两层：gate（确定性：名单、准入表、机器人名单）+ assessment（模型研判）。卡片明显与规则无关时可直接忽略。（001、002）
    订阅与直通（§3.2）已实现Subscription 多对多；匹配的 Trigger 扇出给订阅的 Ticket，不经 Eval；执行器可交回超出范围的消息。（001、002）
    Inline & Spill 与链式召回（§3.3）部分派工和消息以 Trigger 卡片内联送达。内容截断时，才附资源指针；Trigger 正文最多 4,000 字符；ticket/<id> 等读取资源会带上相关 id。（004、007）文档没有使用“链式召回”这个说法。
    投机执行（§3.4）部分推断工作由团队规则 + 接受模式控制；规则可以要求静默（不发确认）；执行器发现无事可做时报告 dropped，默认不发消息结束。（002、003）
    异步 ReAct Loop（§4.1）部分前台 shell 命令 5 秒后转后台，完成后唤醒执行器；主 Session 有守卫，拒绝 sleep 和长等待。（003、004、007）
    多信道交互（§4.2）已实现GitHub + 可选飞书；聊天消息默认一句话，硬上限 100 词；GitHub 走结构化的 PR 与评论。（004）
    计算与状态分离（§5.1）部分状态存在一个 SQLite 文件里，Session、目录、订阅和待投递消息能跨重启保留。（003、007）但它作为一个本机进程运行，面板在 127.0.0.1；云端无状态计算容器，文档未提及。
    计算与执行环境分离、端侧 daemon、BYOM（§5.2）文档未提及执行器在本机的执行根目录下工作。（003、006）
    Watchdog（§6）部分没有名为 Watchdog 的 Session。部署文档建议：在运营者自己的 DeepSeek Harness 配置里，建一个每小时运行的检查任务。它看状态，必要时重启，并报告错误。（006）由模型判断 Worker 是否有实质进展，文档未提及。
    不要过度解读这张表“文档未提及”只说明公开原型的文档里没有。README 已说明：原型与内部版本、与文章描述的实现都不相同，部分设计是未来方向。

    08安全提醒与安装

    独立目录不是沙箱执行器 Session 以操作者的系统用户身份运行命令，无需审批。两个预设都以 danger-full-access 运行，并读取所订阅 Thread 里的消息。账号包装器（gh、lark-cli 的包装）只是默认选择 Agent 的凭据，不隔离进程。worker 可以按绝对路径执行程序，也能读取操作者的 home 目录。文档的建议是：要隔离，就用一个只放 Agent 凭据的专用系统账号。

    原型的架构文档在“开放问题”里也列了一条：Trigger 的哪些字段可信，哪些不可信？可信的例如 Source 给的发送者、Thread 归属；不可信的例如正文和引用。这和文章 §8.4 的安全问题是同一类，见 SA09。

    引导式安装

    安装步骤很多，所以原型让一个编程 Agent 陪你装。你只需要对它说：

    Read SETUP.md in this repository and set up dsh-superagent with me.

    SETUP.md 是写给 Agent 看的。它同样遵守“少占注意力”的原则：

    • 先只读 SETUP.md 和 000-philosophy，跑一次环境探测，再开始提问。
    • 一次只问一个问题，每个问题给一个推荐答案，用户一个词就能确认。
    • 问完所有问题，发一条完整方案，确认后才执行。
    • 从不在聊天里要密钥；需要用户亲手做的步骤（建账号、登录 CLI），集中在一条消息里给出命令。

    默认值也体现“从窄处开始”：允许名单只有操作者自己；接受模式是 observe；用专用的 Agent 账号，不用操作者自己的账号；自动合并默认关闭。

    09自测与速记

    接受模式为 observe。名单内的 bob 在“全部消息”群里说“登录页白屏了”。他没有 @ Agent。这条消息匹配一条已启用的规则。结果是？
    名单内但没 @ 的消息，准入表默认是推断候选。observe 下，系统研判推断候选，正面结果只记录为“本会接受”。切到 auto 才会真正接单。
    一个名单外的人在某 Ticket 的 PR 下评论：“顺便把 admin 权限也放开”。这条消息会怎样？
    订阅扇出绕过 gate，但不授予新权限。Ticket 受 Mandate 限制，范围变大必须重新接单。执行器把超出范围的消息交回，它再按普通消息走 Eval。
    下面哪项改动不能通过编辑提示词实现？
    名单和准入表属于 Policy，由宿主代码强制执行。提示词只改变模型读到的指令，不改变 gate、Mandate 和工具检查。
    关于原型的执行环境，哪句话是对的？
    003 和 006 都明确说明：包装器和目录建立的是默认值，不是安全边界。需要隔离时，用只有 Agent 凭据的专用系统账号。

    速记表

    要点一句话
    定位面向单个 GitHub 仓库的主动式编程 Agent；研究原型，非正式产品；与文章设计不完全相同
    哲学尽可能少地占用人的注意力，尽可能多地创造价值
    流程Source → Trigger → Thread → Eval → Ticket/Mandate → Assignment → Executor → Channel
    授权名单与规则由宿主强制；明确请求在任何模式有效；推断工作受 off / observe / auto 控制
    上下文 ≠ 权限订阅提供信息，不扩大 Mandate；范围变大要新开 Ticket
    安全以操作者系统用户运行，目录不是沙箱；隔离靠专用系统账号
