SA03 · 核心架构

事件驱动（上）：过滤与路由

Super-agent 要“主动”，先得改变驱动方式：不再等人敲提示词，而是监听环境里的事件。可环境里绝大多数事件都是噪音。本课讲事件进门的头两关：怎样便宜地滤掉噪音，怎样把剩下的事件快速送到对的地方。

原文：§3 开头、§3.1 事件过滤、§3.2 事件路由阅读约 18 分钟含 2 个互动演示、3 张原文图

学完本课，你能够：

  • 说出什么是 Trigger、什么是 Thread，以及事件生命周期的四个问题。
  • 用 Fast Path / Slow Path 解释两级过滤：程序层管什么，语义层管什么。
  • 说清订阅与直通怎样给 Router 减负，以及多对多订阅的作用。
  • 引用原文实验说明直通的真实价值：省 Router 的决定和 token，而不是提速。

01驱动方式变了：从提示词到 Trigger

先说结论：要让 Super-agent 具备“主动”性，首先要改变系统的驱动方式。

单 Session 模式

主要输入：人在 Session 里逐条键入的提示词。

人下指令，Agent 才被动执行一次。

Super-agent

主要输入：环境中的半结构化事件。

Agent 监听并响应这些事件，不必等人下指令。

原文把这些环境事件叫作 Trigger。例子有：群聊消息、邮件与日程提醒、代码审查评论、CI 运行结果。

围绕一条事件从进入到处理的生命周期，原文依次讨论四个递进的问题：

  1. 过滤：用程序与模型结合的两级策略，滤掉大量噪音。3.1 · 本课
  2. 路由：用订阅与直通机制，把事件送给 Worker。3.2 · 本课
  3. 上下文组织：用 Inline & Spill 与链式召回，高密度注入、按需召回上下文。3.3 · SA04
  4. 提前行动：用投机执行，根据环境信号在后台先做。3.4 · SA04

02高噪音、低触发率

接入真实的群聊和代码平台后，事件流有一个显著特征：高噪音、低触发率。绝大多数日常消息不需要 Agent 介入。

如果每个事件都调用大模型从头判断，延迟和算力成本都难以承受。

原文借用了计算机系统里的 Fast Path / Slow Path 思想：

Slow Path
大模型推理

灵活，但成本高、延迟高。留给真正需要语义理解的情况。

Fast Path
确定性代码

把已经明确、稳定的高频判断固化成代码。延迟低，成本低。

补充：Fast / Slow Path 的出处这个思路在网络设备和操作系统里很常见。例如路由器：绝大多数数据包由硬件按转发表直接转发，这是 Fast Path。少数特殊包才交给 CPU 慢慢处理，这是 Slow Path。原则是：让常见情况快，让少见情况对。

03两级过滤

事件进入系统后的第一步是过滤。目标是在调用大模型之前，先用确定性策略筛掉噪音。只有需要语义理解的候选事件才交给模型。原文采用程序策略与大模型相结合的两级过滤：

程序层策略 Fast Path

按确定性条件直接用代码做准入检查：事件来源、群组范围、用户或机器人白名单。

例如：对不同来源分别设置“仅响应明确请求”“作为候选事件”或“直接忽略”。

在调用模型前，滤掉大部分无关消息。

语义层策略 Slow Path

通过程序层的候选事件交给 LLM。LLM 按“用提示词写的策略”和上下文，判断要不要行动。

它同时是面向人的自然语言扩展点：随时可以用提示词开关或新增策略。

游乐场：配置两级过滤，看多少消息到了大模型
语义层策略（提示词）：
    先看默认配置：闲聊群只认明确请求，机器人消息直接忽略。程序层就滤掉了大部分噪音，不花一次模型调用。
    试着把“闲聊群”改成“作为候选事件”，看进入大模型的条数怎么涨。再关掉“静默复现并修复”，看同样的候选事件怎样变成“不行动”。
    消息是虚构的示例。来源、策略选项和“静默复现并修复”策略名取自原文；具体的判断由本页按简单规则模拟，真实系统里由 LLM 根据提示词判断。
    两层的分工程序层回答“这条消息有没有资格让模型看一眼”。语义层回答“看了之后，值不值得做”。前者便宜、死板、可审计；后者灵活、贵、可以用自然语言随时改。
    注意明确请求“仅响应明确请求”不等于“全部忽略”。设成这一档的来源，明确请求（例如 @agent 帮我…）仍然能通过。

    04事件路由：订阅与直通

    过滤之后，事件要送到对的会话。这里有一个隐患：第 2 节的全局 Router 层负责维持跨信道的连续性。如果已分配任务的每个后续事件仍要经过 Router 转发，这个全局节点依然会承受大量负载。系统的响应延迟也会升高。

    所以 Fast / Slow Path 同样适用于路由。全局 Router 只负责两件事：新任务的冷启动，和跨任务协调。已经确定归属的后续事件，由程序直接发给对应的 Worker，不经过 Router。

    先认识 Thread

    实际工作流里，连续事件会形成一条事件流，原文叫 Thread。例如同一个 GitHub Pull Request、同一个 IM 话题或同一封往来邮件串下的事件。

    两条路径

    Router 根据某个 Thread 的初始事件创建 Worker Session 后，这个 Worker 直接订阅对应的 Thread。事件路由于是分成两条路径：

    已订阅 Fast Path

    同一 Thread 的后续事件，由程序直通已订阅的 Worker。Router 不需要再调用工具转发。

    新事件超出当前任务范围时，Worker 可以取消订阅，或交回 Router 重新分派。

    未订阅 Slow Path

    Router 仍能观测所有事件，掌握全局状态。

    但它只负责判断和分派还没有 Worker 订阅的新事件。

    订阅是多对多的

    一个 Worker 可以同时订阅多个相关 Thread。多个 Worker 也可以订阅同一个 Thread。多个 Worker 在同一个工作环境或讨论里发生交集时，这个 Thread 的新事件会同时直通给所有订阅者。它们不需要点对点通信，也有机会获知彼此的操作，自行解决冲突。

    输出侧不变：Worker 仍把关键结论汇报给 Router，由 Router 统一回复用户，并同步全局记忆。

      05直通值多少：实验数字

      原文 7.1 节的消融实验专门去掉了直通，结论很清楚：直通不提速，但省 Router 的力气。

      方案任务完成时间 p50 / p95（分钟）单次实验读缓存 token（全部 Session）
      Super-agent12.4 / 15.72323 万
      Super-agent，去掉直通12.6 / 15.53177 万
      • 去掉直通后，任务完成时间与完整版基本一致。
      • 单次实验里，Router 要做的决定增加约 30%。
      • 总读缓存 token 从 2323 万增加到 3177 万，增幅约 37%。
      这表明在实验负载下，直通机制不提高任务完成质量与速度，但为 Router Session 节省了可观的 token 与推理开销。§7.1
      读数字的限定实验基于合成负载与简化环境（约 300 条消息、约 20 条工作请求，每种方案跑 5 次）。原文说结果“仅作为初步参考”。上面演示里的决定数增幅比 30% 大，是因为脚本里后续事件占比高；不要把演示数字当成实验结论。完整实验见 SA07。
      补充：为什么不提速原文 7.2 节的压测解释了这一点。Router 有批处理，峰值负载变大时也没触及单个 Router 的吞吐瓶颈（见 SA02）。所以直通省下的是 Router 的推理和 token，而不是用户等待的时间。规模更大时，Router 离瓶颈更近，直通的意义可能更大——这是推论，原文没有测。

      06自测与速记

      两级过滤里，“对不同来源分别设置仅响应明确请求、作为候选事件或直接忽略”属于哪一层？
      这是按来源做的确定性准入检查，用代码完成，属于程序层（Fast Path）。语义层由 LLM 按提示词写的策略做判断。
      原文为什么说语义层是“面向人类的自然语言扩展点”？
      语义层策略是写在提示词里的。改行为不用改代码，用自然语言加一条、关一条就行，例如“静默复现并修复”。
      一个 Worker 正在处理某 PR，PR 下来了一条新评论，内容超出了它的任务范围。按原文，它可以怎么做？
      原文：若新事件超出了当前任务的范围，Worker 也可取消订阅或交回 Router 层重新分派。Worker 不直接对人说话，也不负责分派新任务。
      原文消融实验中，去掉直通机制带来的主要变化是？
      直通不提高完成质量与速度。但它为 Router 节省了可观的 token 与推理开销：去掉直通后，读缓存 token 从 2323 万增加到 3177 万。
