读懂实验：消融与批处理

原文用两组初步实验检验核心的调度与路由设计。第一组比较整套系统；第二组单独给 Router 加压。本课带你读懂每一个数字，以及它们没说明什么。

原文：§7 初步实验阅读约 18 分钟含 2 个互动演示、3 张原文图

学完本课，你能够：

  • 说出消融实验的设置，以及它衡量的是调度能力，而不是单任务执行能力。
  • 用 p50 / p95 比较四种方案，并解释单 Session 方案慢且不稳定的原因。
  • 说明直通机制在实验里省下了什么、没改变什么。
  • 解释 Router 的批处理为什么“越忙越划算”，以及它的上限。
  • 说出读这组实验时要保留的限定条件。

01实验在测什么

先说结论：这组实验只测“调度与协作”，不测“把单个任务做得多好”。原文分两层做：

  1. 端到端消融实验（§7.1）：对比双层架构、订阅直通与单 Session 方案。
  2. Router 层压力测试（§7.2）：单独测试 Router 的批处理。
设置项原文中的取值
驱动方式群聊和 GitHub CI 消息流同时驱动四种端到端方案
单次实验规模约 300 条消息，其中约 20 条是工作请求；其余是闲聊、跟进、叫停和 CI 消息
编码工作用一个只消耗时间的工具代替
重复次数每种方案重复运行 5 次
时间缩放消息间隔与工作时长按 1/4 缩放；模型调用耗时为真实值
完成时间从工作请求到结果消息的耗时
关键限定编码工作用只耗时的工具代替，因此实验衡量的是系统的调度与协作能力，而非对单个任务的执行能力。

02四种方案与两句提示词

Super-agent

完整的双层架构 + 订阅直通。

Super-agent，去掉直通

后续事件也要经 Router 转发。用来单独看直通机制的作用。

单 Session + Subagent 工具，中性提示

一个主会话收所有消息，可以调用 Subagent。分不分工由模型自己判断。

单 Session + Subagent 工具，提示优先委派

同上，但提示词明确鼓励把工作交给 Subagent。

两种单 Session 方案只差一句提示词。原文给出了原句：

中性提示：

"Use a subagent for a piece of work when appropriate..."

提示优先委派：

"Every message of the chat reaches you, so work you run yourself keeps stopping for new messages. Prefer handing each piece of work to a subagent of its own, and do only small things yourself..."
补充：第二句提示在说什么大意是：“聊天里每条消息都会到你这里，所以你自己干的活会不断被新消息打断。优先把每项工作交给它自己的 Subagent，你只做小事。”它其实是用提示词把双层架构的原则“教”给模型。实验要回答的问题之一，就是“靠提示词教”和“靠系统结构保证”有什么差别。

为什么单 Session 方案慢且不稳定

原文的解释：带 Subagent 的单 Session 方案受提示词影响很大。主 Session 常常决定自己直接执行任务。

  • 中性提示：5 次运行中，模型一次都没有调用 Subagent。所有工作都在主 Session 里进行，并不断被新消息打断。p95 达到 29.5 分钟。
  • 提示优先委派：5 次运行中有 4 次进行了委派，完成时间有所缩短，但整体仍慢于 Super-agent。剩下 1 次，模型判断工作“很小”而选择自己执行，形成图 12 中的紫色长尾。
相比于在单 Session 中依赖提示词工程和模型临场判断分不分工，双层架构通过让 Router 不直接执行具体工作、Worker 仅接收所订阅 Thread 的消息，在系统层面上缓解了这一问题。§7.1
要点“优先委派”的 p50 是 13.8 分钟，已经接近 Super-agent 的 12.4。差距主要在 p95（29.0 vs 15.7）。也就是说，提示词能把多数情况教对，但保证不了每一次。结构上的约束（Router 不配执行工具）才能消掉这条长尾。

04结果二：直通省了什么

先说开销。由于维护了多个独立会话，Super-agent 单次实验的读缓存 token 高于单 Session 方案。原文的总结是：以更多的 token 消耗，换取更短且更稳定的完成时间。

再看直通。在 Super-agent 内部去掉直通之后：

约 +30%

原文结论在实验负载下，直通机制不提高任务完成质量与速度，但为 Router Session 节省了可观的 token 与推理开销。

为什么去掉直通，速度却没变慢？答案在下一节：Router 在压力下会自动批处理，峰值负载增加了，仍没碰到单 Router 的吞吐瓶颈。

05Router 的批处理

先说结论：单个常驻 Router Session 没有想象中那么容易成为瓶颈。它越忙，每个决定分摊到的推理时间反而越短。

测试方法：Router 调用真实模型，Worker 使用 Mock 模型。需要决定的 Trigger 到达速率，从每分钟约 1 条逐步提升到约 40 条。观察三个量：平均 batch 大小、单次请求耗时、单个决定分摊的推理时间。

指标约 1 条/分约 40 条/分变化
平均 batch 大小1.02.8×2.8
单次请求耗时2.5 秒3.9 秒×1.56
单个决定的分摊推理时间6.4 秒1.6 秒降到 1/4

为什么合并处理几乎不加钱

  1. 积压自动成批。上一轮推理期间到达的 Trigger 会积压下来，在下一次 LLM 调用中一并注入。
  2. Router 每步是“长输入、短输出”。它只做轻量的交互与分派，输出很短。
  3. 长输入在 Prefill 阶段并行计算。多加几条 Trigger，只是让输入变长一点。单次请求耗时的增长远慢于批处理大小。

曲线上的 7 个点是课程作者从原文图 14 目测读出的近似值，两点之间线性插值。原文文字给出的端点是：batch 1.0→2.8、单次请求 2.5→3.9 秒、分摊 6.4→1.6 秒。
补充推测：分摊时间为什么比单次请求还长在低负载下，每个决定分摊 6.4 秒，比单次请求的 2.5 秒还长。一个可能的解释是：Router 做出一个决定，可能需要不止一次 LLM 调用（例如先调用工具查询，再回复或分派）。原文没有说明这一点，这里只是推测。

批处理的上限

原文给了两个上限：上下文长度，以及模型在一轮中能准确处理多少条 Trigger。在一定范围内，积压越多，分摊越低；超出这个范围，合并就会出错或放不下。

原文的结论：这解释了为什么去掉直通使 Router 峰值负载增加后，仍未触及单 Router 的吞吐瓶颈。因此在目前的团队规模下，无需过早对 Router 层做水平切分而牺牲全局上下文的连续性。

06读实验的注意事项

原文自己说：实验基于合成负载与简化环境，部分设置还可以更加严谨，结果仅作为初步参考。读这组数字时，把下面几条放在心上。点一下可以打勾。

  • 合成负载。约 300 条消息是构造的，不是真实团队的一天。
  • 工作被替换成计时工具。结果只说明调度与协作，不说明 Super-agent 写代码更好。
  • 时间按 1/4 缩放。消息间隔与工作时长缩放了，模型调用耗时是真实的。缩放会改变“模型调用耗时”在总时间里的占比。
  • 样本少。每种方案 5 次；p95 在 5 次运行的任务里统计，单次异常（如紫色长尾）影响很大。
  • token 换时间。Super-agent 更快更稳，但读缓存 token 是单 Session 方案的 2–4 倍。是否划算取决于你更在乎什么。
  • 规模条件。“单个 Router 够用”是“在我们目前的团队规模下”的结论。
