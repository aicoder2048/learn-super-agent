SA05 · 交互与运行

面向人的交互：全双工与多信道

双层架构从上下文层面保证了连续。但人真正感受到的，是“它干活时还理不理我”和“它说话吵不吵”。这一课讲原文怎样在交互方式和交互渠道上解决这两件事。

原文：§4 面向人的交互阅读约 15 分钟含 2 个互动演示、1 张原文图

学完本课，你能够：

  • 说明经典 ReAct Loop 为什么是半双工，阻塞发生在哪一步。
  • 描述异步 ReAct Loop 的 start() / stop() 机制，并用时间线比较两者的响应等待。
  • 说出 IM 类即时信道与 GitHub/邮件类异步信道的输出规范，包括“单次回复不超过 100 词”。
  • 解释双层架构如何天然地把冗长推理和工具调用挡在外部信道之外。

01两个交互问题

先说结论：要在真实的人机交互里同时做到连续和高效，原文认为还要解决两个问题。

问题一 · 交互方式 · §4.1
别让后台阻塞前台

后台在跑耗时操作时，会话也要能随时接受新指令，不必等上一个命令或任务完成。解法：异步 ReAct Loop。

问题二 · 交互渠道 · §4.2
输出匹配信道

交互发生在用户熟悉的不同工作信道里。系统的输出方式要匹配这个信道的带宽和人的使用习惯。

补充：和第 2 课的关系双层架构（SA02）解决的是“用户面对的始终是同一个 Agent”。但这个 Agent 可能每做一件事就“失联”几分钟，也可能把推理过程刷满群聊。这样用户仍然觉得它不好用。§4 补的就是这最后一公里。

02经典 ReAct Loop 为什么会“卡住”

在经典 ReAct Loop 中，模型发起一次同步的 run() 工具调用后，循环会阻塞。它要等工具执行完毕、返回最终结果，才进入下一步。在这期间，会话无法响应任何新的用户输入。

这就是半双工：像对讲机，一方说完，另一方才能说。要消除阻塞，就要把对话从一问一答的半双工模式，转变为全双工模式。

看图要点上半部分中间的虚线框“同步阻塞等待工具返回”，就是用户干等的时间。下半部分，同样长的工具在后台跑，前台却插进了“用户消息 2 → LLM Call 即时回复”。工具完成后，结果作为“新消息投递”进来，再由一次 LLM Call 交付。

03异步 ReAct Loop（动手）

原文的做法：把耗时的命令和子任务工具调用改成异步的 start() 和 stop()，构成异步 ReAct Loop。

  1. 模型调用 start() 后，立即收到“已启动（Started）”的返回。循环不再等待这个工具。
  2. 后台工具执行完成后，系统把最终结果作为一条新的事件消息投递进会话。
  3. 模型也可以根据上下文调用 stop()，主动终止执行时间过长的后台命令。

这样，前台对话响应和后台任务执行就解耦了。Agent 在后台跑耗时任务时，也能响应人的输入。新输入在当前推理步结束后即被处理，不必等后台工具完成。

原文限定这一异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。
演示：用户在工具运行时发来第二条消息
LLM 推理步工具在跑前台阻塞stop() 终止的工具竖线：消息 2 到达
拖动“消息 2 到达”。经典版里，不管消息何时到，都要等工具跑完。异步版里，等待 = 当前推理步还剩的时间 + 回复的那一步，和工具耗时无关。
把消息 2 拖到刚收到 Started 的那几秒里。你会看到异步版也要稍等。原因是模型正在处理 Started 通知，新输入要等这一步结束。
勾选“停下”，看 stop() 能省掉多少白跑的工具时间。
简化模型：时间轴从模型发起工具调用算起，工具在第 4 秒开始；每个 LLM 推理步固定 4 秒；经典版在工具返回后，下一步同时看到结果和消息 2。数字只用来说明机制，不是原文实验。
补充：熟悉的影子这是操作系统和网络编程里“阻塞 I/O → 异步 I/O”的老路。程序发起读请求后不干等，先去处理别的事。数据到了，系统再用事件通知它。start() 像提交一个异步请求，“结果作为新事件投递”像完成回调，stop() 像取消请求。这个类比是课程作者的解释。

04多信道交互

先说结论：不同工作信道的信息密度和交互习惯不同，系统的输出要与之匹配。

反面例子是：把面向单人终端的交互方式直接搬进群聊。冗长的推理过程和密集的工具调用都原样输出。在多人协作中，这极易造成信息过载。

双层架构已经解决了一半具体任务中冗长的推理过程和密集的工具调用，都被隔离在 Worker Session 内部，不会直接输出到外部信道。对外交互由 Router 层统一负责。

在此基础上，系统还要做两件事：接入用户日常使用的工作环境；用提示词为不同信道定制交互规范：

IM 等即时通讯信道

侧重低打扰的轻量沟通。

  • 像人类同事一样，只在需要决策或验收时发送通知。
  • 只问直接问题，给简短结论。
  • 原文验证过的一条简单有效的硬性规定：单次回复不超过 100 词。

GitHub、邮件与文档等异步信道

侧重结构化、高信息密度的异步交付。

  • 创建或更新 Pull Request 时，按项目规范写完整的问题背景、改动说明与验证结果。
  • 个人助手场景下，直接起草结构化的邮件与文档摘要。
补充：为什么规则写在提示词里信道规范是“软规则”：它描述语气、长度、什么时候说话。原文选择用提示词表达，团队可以随时用自然语言调整。开源原型也是这样做的：团队提示词里有 Communication（沟通方式）一节（见 SA08）。

    06自测与速记

    在异步 ReAct Loop 中，模型调用 start() 后会发生什么？
    原文 §4.1：调用 start() 后立即收到 Started；后台工具完成后，系统再把最终结果作为一条新的事件消息投递进会话。
    异步 ReAct Loop 下，Agent 什么时候处理用户的新输入？
    原文原话：“新输入在当前推理步结束后即被处理，不必等待后台工具完成。”它不打断当前的推理步。
    关于异步任务机制在 DeepSeek Harness 中的状态，原文怎么说？
    原文 §4.1 末句：“这一异步任务机制已经在 DeepSeek Harness 中实现，但尚未默认开启。”
    原文在 IM 信道验证过的一条简单有效的硬性规定是？
    原文 §4.2：IM 侧重低打扰的轻量沟通，只在需要决策或验收时通知，只问直接问题、给简短结论；验证过的硬规定是单次回复不超过 100 词。
