存算分离与 Watchdog

“持久”这个特征靠两个模块支撑。存算分离让 Agent 不再跟着某一台电脑开机关机。Watchdog 从系统外部盯着它，出了问题就修。

原文：§5 计算、状态与环境的分离 · §6 Watchdog阅读约 18 分钟含 2 个互动演示、1 张原文图

学完本课，你能够：

  • 说出本地 Agent 把哪三样东西绑在同一台设备上，以及这带来的两个后果。
  • 解释存算分离的两步解耦：计算与状态分离、计算与执行环境分离。
  • 说明为什么不把执行环境搬上云，而是用端侧 daemon 让环境留在原地。
  • 比较原文设计与 Anthropic“脑手分离”的异同。
  • 说出 Watchdog 比传统存活探测多看了什么。

01问题：三样东西绑在一台机器上

先说结论：现有的本地 Agent 把三样东西默认放在同一台设备上。设备一离线，Agent 就停了。

① 计算
推进 Agent Loop

调用模型、解析结果、决定下一步调用哪个工具。这是 Agent 的“大脑在转”。

② 状态
会话状态

需要持久保存的东西：消息历史、任务进度、订阅关系等。

③ 环境
执行环境

代码仓库、本地工具链、依赖服务。命令真正在这里运行。

原文指出两个后果：

  • 设备休眠或离线，Agent 就停止运行。这违背了“持久”特征。
  • Agent 无法访问其他设备上的环境。它只能在自己所在的这台机器上干活。

解决办法是借用存算分离（Compute-Storage Separation）的思想，分两步解开这三者的绑定。

步骤解开什么换来什么原文
第一步计算 ↔ 状态Agent 摆脱单机生命周期，云端持久在线§5.1
第二步计算 ↔ 执行环境真实工作环境留在原地，可跨设备访问§5.2

02第一步：计算与状态分离

关键观察：推进 Agent Loop 的计算可以做成无状态的。真正需要持久保存的，是会话状态。

  1. 计算上云：把 Agent Loop 放进云端无状态的弹性计算容器。
  2. 状态入库：把 Session 等持久化状态存进数据库。
无状态计算容器可以水平扩展、重启或替换，会话与任务的连续性则由持久化存储保障，从而使 Agent 摆脱单台本地设备的生命周期限制，实现云端持久在线。§5.1
补充：存算分离的“前辈”云数据库（例如 Snowflake、Aurora）把查询计算节点和存储层分开。计算节点随用随开，数据始终在共享存储里。
Web 后端也常这样做。应用服务器不保存状态，会话放进 Redis 或数据库。这样任何一台服务器都能接着处理同一个用户。
原文把同样的思路用到 Agent Loop 上。

03第二步：计算与执行环境分离

Agent Loop 和会话状态上云之后，新问题来了：任务需要的执行环境在哪里？

原文有一个重要观点。模型工作所需的上下文，很大一部分来自执行环境：代码仓库、本地文件、依赖服务等。模型要通过工具调用去取。从这个意义上说，广义的上下文也包含执行环境本身。

两种常见思路，为什么不理想

思路 A：云端沙箱重建环境

在云端启动沙箱，拉取代码，尝试重建并同步环境。

真实环境往往包含未提交的本地修改、私有凭据、内网服务依赖、特定硬件或工具链。同步成本高，还容易遗漏信息。

思路 B：让用户迁到云端

要求用户放弃本地环境，直接在云端工作。

对很多用户来说，迁移成本过高。

原文的做法：环境留在原地

Agent Loop 在云端运行。重状态的执行环境留在原地。端侧只装一个轻量 daemon。

daemon 不保存会话状态，只负责执行命令、返回结果。Agent 按需读取环境里的上下文。

核心句既然难以复制和同步的是环境本身，就不必让执行环境跟着 Agent Loop 上云。

图 11 下方的三类执行环境，对应这种设计的两种用法：

  • BYOM（Bring Your Own Machine）：把你日常用的开发机或个人电脑接入云端 Agent。
  • 云端托管机器或按需创建的计算环境：同样用 daemon 接入。

结果是：一个 Agent 不再受限于单台机器。它可以在不同执行设备之间切换，按任务需要选环境。它甚至支持间歇在线的设备。某台个人设备重新上线后，云端 Agent 会自动触发那台设备上的任务，并完成它们。

与 Anthropic“脑手分离”的异同

Anthropic“脑手分离”Super-agent（原文 §5.2）
相同点harness 保持无状态；会话日志存放在 harness 之外；通过统一接口按需接入执行环境。
场景托管服务首先接入用户日常使用的个人机器
执行环境按需创建的沙箱、客户 VPC 内的资源可能间歇在线的个人机器，上面有未提交的修改和本地凭据
代价：信任前提这套设计默认云端与端侧环境彼此受信任。原文在 §8.4 专门讨论了它的安全隐患。攻击者一旦攻破云端 Agent Loop，所有连接的端侧设备都面临风险。详见 SA09。

05Watchdog：外部控制回路

先说结论：只靠存算分离还不够。持久在线还要求系统在长期运行中能从异常中自动恢复。原文的办法是在主系统之外，再放一个独立的 Agent 会话来看守它。

原文给了两条理由：

  1. 需要外部回路。持久在线的分布式系统，很难仅靠主系统内部逻辑保证长期可靠运行。需要在主系统之外引入独立的外部控制回路，即 Control Loop。
  2. 要看任务，不只看进程。在 Agent 系统里，许多异常并非进程崩溃，而是模型在执行中陷入无效循环或偏离目标。所以不仅要监控基础设施的存活，还要监控任务本身的进展。
怎么驱动
定时消息

Watchdog Session 由定时消息驱动，构成主系统外部的 Control Loop。

看什么
基础设施 + 任务进展

处理接口报错、状态恢复失败等基础设施故障。由模型判断各个 Worker 是否有实质进展、方向是否偏离整体目标。

怎么处理
介入修复 / 持续复查

发现异常时及时介入修复。遇到外部偶发故障，则持续复查直至恢复正常。

额外好处
能对话的运维

Watchdog 本身是具备完整工具能力的 Agent Session。维护者可以用自然语言问它故障原因。也可以让它在线修正主系统，例如增删提示词、调整触发规则。

模拟：存活探测 vs Watchdog Session
监控方式：
正常推进出故障、没人管已发现、等待修复或复查修复后继续竖线 = Watchdog 定时检查
切换两种监控方式对比。
出现“无效循环”和“偏离目标”时，进程活着，也不报错。存活探测发现不了，任务一直空转到结束。Watchdog 让模型判断任务有没有实质进展，所以能发现。演示用“比较前后两次检查的进展”来简化这个判断；原文没有规定判断方法。
外部偶发故障修不了。Watchdog 就在每次定时检查时复查，外部恢复后马上让任务继续。
简化模型：模拟 70 分钟。Watchdog 发现基础设施故障后 2 分钟修好；发现“无效循环”需要连续两次检查都没有进展；发现“偏离目标”需要故障出现至少 5 分钟、产出足够判断。外部故障在第 50 分钟自行恢复。数字只用来说明机制，不是原文实验。
补充：看门狗与控制器“Watchdog”一词来自硬件看门狗定时器。程序要定时“喂狗”。超时没喂，定时器就判定系统卡死，并强制复位。Kubernetes 的控制器是另一个熟悉的 Control Loop：不断比较“期望状态”和“实际状态”，有差距就纠正。原文的 Watchdog 更进一步：它让模型来判断“实际状态”里任务有没有真正进展。
补充：为什么放在主系统之外原文只说需要主系统外部的独立 Control Loop，没有展开理由。课程作者的理解是：如果 Watchdog 跑在 Router 或某个 Worker 里，主系统卡死时它也一起卡死。独立的会话加独立的定时触发，才能在主系统失灵时仍然工作。

06自测与速记

原文第一步解耦后，什么东西放进了数据库？
计算可以无状态，放进云端弹性容器；需要持久保存的是会话状态，存进数据库。
为什么原文不把执行环境同步到云端沙箱？
难复制、难同步的是环境本身。所以让环境留在原地，用一个不保存会话状态的轻量 daemon 接入。
端侧 daemon 负责什么？
原文：仅在端侧部署一个不保存会话状态的轻量 daemon，它只负责执行命令与返回结果。
Watchdog 能发现、而传统存活探测发现不了的异常是？
这类异常里，进程活着、也不报错。只有让模型判断 Worker 是否有实质进展、方向是否偏离整体目标，才能发现。
遇到外部偶发故障（例如外部服务暂时不可用），Watchdog 怎么做？
原文：发现异常时及时介入修复，遇到外部偶发故障则持续复查直至恢复正常。
