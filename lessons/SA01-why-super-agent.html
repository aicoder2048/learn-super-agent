SA01 · 问题与全景

为什么需要 Super-agent

模型越来越能独立完成单个任务。新的瓶颈不在模型，而在人能同时盯住几件事。Super-agent 要做的，是让人从“管理一堆会话”里解放出来。

学完本课，你能够：

  • 解释“单任务上限看模型，多任务上限看注意力”这句话，并用模拟说明它。
  • 说出现有单 Session Agent 在多任务、团队协作下的三个限制。

01人的角色在上移

先说结论：人正在从“盯着执行”转向“做决策、做验收”。原文用两个变化说明这一点。

变化一 · 单任务
越来越少需要人盯

以 Coding Agent 为代表的单任务 Agent 已经证明：模型能用工具解决复杂问题。它需要的持续监控和逐步干预越来越少。

变化二 · 多任务
多 Agent 协同变得可行

模型的多 Agent 协同能力也在提升。跨会话的组织与调度因此变得可行。

能力的提升催生了新的应用形态。近期，个人助手（Personal Agent）集中涌现。它们直接接入消息、日程、邮件和工作平台，持续观察信息流，协助处理事务。

原文强调：这种持续在线、事件驱动的工作模式不只属于个人场景。在软件开发等商业场景里，它同样很有价值。

随着人类在底层执行中的参与减少，人的角色正逐步上移到更高层的决策与验收。§1

02瓶颈转向人的注意力

现有主流 Agent 以单一 Session 为基本工作单位。不同 Session 彼此独立。你同时推进多项工作时，必须手动切换会话，并记住每个会话里聊过什么。

原文给了一个观察数字：一个人通常只能同时跟进 3 到 5 个活跃 Session。

本课核心句在这种设计下，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。

下面的模拟把这句话变成可以动手验证的模型。每个 Session 里，Agent 先独立干一段活，然后停下来等你：你要读它的进展、回一句话。从一个 Session 切到另一个 Session，你还要花时间“找回状态”。你只有一个人，一次只能处理一个 Session。

简化模型：模拟 2 小时；每次处理 1.5 分钟；Agent 工作时长在设定值的 50%–150% 之间随机；你按先来先服务处理。图中只画前 60 分钟。数字只用来说明机制，不是原文实验。
补充：为什么是 3–5 个在默认参数下，每个 Session 每轮占用你约 2.5 分钟（处理 1.5 + 切换 1），每轮约 10 分钟。你的时间大约能撑起 4 个 Session。这和原文观察到的“3 到 5 个”在同一量级。
注意两个口径不同。“撑起 4 个”指你的时间刚好用满（演示里利用率约 84%）。演示读数里的“约 5 个后增长不到 10%”指总产出开始变平。前者先到，后者稍晚。模型越能独立工作，这个数越大；切换代价越高，这个数越小。

03简单扩展为什么不够

一个直觉做法是：在现有的本地单会话 Agent 上，用 CLI、MCP 或外部连接器接入消息。原文认为，这样 Agent 虽然能收到外部消息，但仍有三个问题，需要大量人工维护。

① 单会话同步阻塞

一个会话一次只做一件事。它跑长任务时，新消息只能排队。

② 多任务上下文混乱

多项任务的中间细节挤在同一个上下文里，互相干扰。

③ 本地设备离线即停

笔记本合上、休眠或断网，Agent 就停止运行。

要突破这些限制，就要打破 Agent 与单次手动会话的绑定。

04什么是 Super-agent

原文定义使 Agent 成为一个能跨会话保持上下文、同时推进多项复杂任务且互不干扰的连续实体。我们把这种 Agent 形态及其系统架构称为 Super-agent。

注意两点。第一，Super-agent 既指一种Agent 形态，也指支撑它的系统架构。第二，关键词是“连续实体”：对用户来说，始终只有一个 Agent。

05四个基础特征

原文认为 Super-agent 具备四个基础特征。记住这四个词，后面每一课都会回到它们。

特征 1
连续

你在 IM、GitHub 评论等熟悉的界面和它交互，感觉始终只有一个 Agent。你不用去想“Session X 里有没有 Y 信息”。例如：先在 IM 定了方案 A，再在 PR 评论里改成方案 B，它能理解并调整方向。

特征 2
高效

交互响应快，同时能并行、高质量地完成多个复杂任务。不用等上一个任务完成，就能接下一条指令。

特征 3
主动

不等你逐条下指令。它持续观察环境事件，主动推进值得处理的事。不需要它时，保持安静。

特征 4
持久

始终在线，直接接入你真实的工作环境。长期运行中遇到异常，能自动恢复。

常见误解“主动”不等于“话多”。原文的“主动”包含后半句：不需要介入时保持安静。主动是指“自己发现值得做的事”，不是“频繁打扰人”。

原文接着指出：单个 ReAct Loop 无法同时支持这四个特征，底层需要一套相应的架构。

06五个模块：全景图

原文的核心判断是：相似的设计约束会导出相似的架构选择。个人助手也好，软件开发场景的 Agent 也好，目标都是“持续在线、并发响应环境事件”。目标相同，底层就可能采用相近的架构。这些问题和传统计算机系统长期讨论的问题高度相似。所以，很多经典设计思想可以直接借用。

07自测与速记

按原文的说法，在以 Session 为单位的设计下，多任务的上限取决于什么？
原文：“单任务的上限取决于模型能力，多任务的上限取决于人的注意力。”一个人通常只能同时跟进 3 到 5 个活跃 Session。
下面哪一项不是原文列出的“简单扩展”方案（在本地单会话 Agent 上接 CLI/MCP/连接器）的问题？
原文列的三个问题是：单会话同步阻塞、多任务上下文混乱、本地设备离线即停止运行。单任务 Agent 已经证明了模型调用工具的能力。
“主动”这个特征的完整含义是？
主动包括两半：自己发现值得做的事，以及没事时不打扰人。人们常常忽略后者。
“持久”这个特征主要由哪两个模块支撑？
原文：通过计算、状态与环境的分离（第 5 节）及 Watchdog（第 6 节），实现跨设备的持久在线与异常自愈。
