SA02 · 核心架构

双层架构：Router 与 Worker

一个会话很连续，但慢；很多会话很快，但割裂。双层架构把“维护全局连续性”和“高并发执行”拆到两个层级，两头都要。

原文：§2 双层架构（2.1 Router 层、2.2 Worker 层）阅读约 18 分钟含 2 个互动演示、1 张原文图

学完本课，你能够：

  • 说清会话组织上“连续性与吞吐量”的根本权衡，以及两个极端方案各自的问题。
  • 说出 Router 层和 Worker 层各自负责什么、不负责什么、该配什么模型。
  • 区分双层架构与常见的 Agent Team。
  • 用批处理机制解释：为什么单个常驻 Router Session 不容易成为瓶颈。

01根本权衡：连续性与吞吐量

先说结论：会话的组织方式是一道二选一的题。你想同时要跨信道的“连续”和多任务的“高效”，就绕不开它。原文把它叫作连续性与吞吐量的根本权衡（Trade-off）。

极端一：所有事件进同一个 Session

✓ 上下文最连续。

✗ 慢。单个 ReAct Loop 串行执行，有速度上限。任务完成耗时长，吞吐低。

✗ 互相干扰。多个任务的中间细节混在一起，会影响完成效果。

极端二：每个事件新开一个 Session

✓ 并发吞吐最高。

✗ 结果割裂。任务之间并不完全独立。缺少全局上下文，各个 Session 的结果彼此割裂。

✗ 交互混乱。多个 Session 各自向用户回复。

下面的模拟用同一串事件，比较这两个极端和双层架构。事件里有 4 个任务（A–D），其中两条是“跟进”：用户改主意，或补充要求。

模拟：同一串事件，三种组织方式
执行任务按跟进调整缺上下文 / 结果冲突Router 路由与分派
事件顺序：A 新任务 → B 新任务 → A 跟进：改用方案 B → C 新任务 → B 跟进：补一个测试 → D 新任务。
看三处：①最后一个任务何时完成；②有几个“声音”在回复用户；③“A 改用方案 B”这条跟进，有没有送到真正在做 A 的地方。
简化模型：跟进事件需要额外 40% 的执行时间；Router 每次路由耗时 0.3 分钟。这里 Router 把跟进转给已有 Worker；SA03 会讲更快的“订阅与直通”。数字只用来说明机制，不是原文实验。
看模拟要点把“事件间隔”调小，让事件变密。单 Session 方案的“全部完成”时间停在 48 分不变。事件一直在排队，这个时间只由总工作量决定。变长的是它的“平均任务耗时”：后到的事件要等前面的长任务做完。这叫队头阻塞。
另两种方案随事件变密越来越快，和单 Session 的差距拉大。“每事件一个 Session”最快。但 A 的跟进进了一个新 Session，它对 A 一无所知。原来那个 Session 还在按方案 A 干活。

02拆成两层

为了兼顾连续性与吞吐量，原文把两件事拆到两个层级：

  • 常驻的 Router 层统一承接人类交互，负责全局协调。
  • 上下文隔离的 Worker 层并发执行具体任务。

这样，系统在底层接管了上下文管理与并发执行。用户侧感觉不到 Session 的存在，面对的始终是同一个 Super-agent。

让用户手动管理 Session，在很大程度上是从底层 LLM API 延续下来的设计惯性；Session 应当是系统的实现细节，而不应是用户的认知负担。§2

原文还指出一个连带的变化。在现有设计里，Session 同时承担两件事：技术上的上下文管理，和面向用户的项目管理。把产品形态与底层 Session 解耦后，项目管理不再受 Session 限制。“向用户暴露怎样的交互与任务管理方式”变成了一个独立的产品问题。这个问题留到 SA09 讨论。

常见误解“双层”不等于“两个 Session”。原文说明：这是逻辑上的职责划分。每一层在实现上都不必局限于单个 Session，可以有各自的内部结构。

03Router 层：只交互，只分派

Router 层是常驻的全局路由层，承接所有入口的人类交互。所有跨任务的信息与决策都在这里汇总。原文给了它三个身份：

身份 1
全局序点

跨信道的指令在这里排出先后。先在 IM 说方案 A、后在 PR 改方案 B，顺序是确定的。见序点。

身份 2
协调点

任务之间的高层关联在这里处理。少数跨任务协同，也由它中转。

身份 3
记忆

它保存全局上下文。用户跨信道提起旧任务，由它找回来。

设计约束为了不让这个全局节点成为性能瓶颈，Router 层不直接执行具体任务，只负责人类交互与任务分派，甚至可以不配备 Bash 工具。

Router 与 Agent Team 的区别

“一个中心节点分派多个执行节点”，表面上像常见的 Agent Team。原文指出，两者的侧重点不同。

常见的 Agent Team

用于单个复杂任务内部的步骤拆解与角色协作。

子步骤耦合紧。Team Lead 要深入理解任务细节、规划子任务、高频协调成员。

Lead 的推理负载很重。

Super-agent 的 Router

只处理任务之间的高层关联与分派。

不介入单任务内部的拆解。

推理负载轻，可以用较轻量的模型。

反过来也成立。Agent Team 也能变成双层架构，前提是用提示词约束它的主会话：

  • 不亲自执行具体任务；
  • 只负责对外交互；
  • 把不同任务分派给各成员独立推进。
原文实践Router 层的任务常常没有想象中复杂。使用较轻量的模型，往往就能兼顾速度与效果。Router 的内部也不必局限于单个 Session，甚至部分逻辑未必需要调用 LLM。原文选择了最直接的实现：单个常驻 LLM Session。
补充：一个比喻Router 像餐厅前台：接待所有客人，记得每桌点了什么，把单子分给后厨。前台不下厨。后厨（Worker）各做各的菜，不出来和客人聊天。客人改主意时只找前台，前台知道该转给哪位厨师。

04单个 Router 为什么不是瓶颈

所有交互都过一个 Session，它会不会挤爆？原文的答案是：没有表面看起来那么容易。原因是批处理（Batching）。

Router 在推理一轮时，新到的环境事件（Trigger）会积压下来。下一轮，这些积压事件一并处理。合并的额外开销很小。

  • 事件流平稳时：Trigger 逐条进入 Router Session，单次响应延迟低。
  • 事件密集涌入时：上一轮积压的多条 Trigger 自动合并，在下一次 LLM 调用中一并注入。

为什么合并很便宜？Router 只做轻量的交互与分派，每步通常是长输入、短输出。多条 Trigger 合进一次 API 调用，会在 Prefill 阶段并行计算。单次请求耗时的增长，远慢于批大小的增长。所以在一定范围内，积压越多，单个决定分摊的推理时间越低。

上限取决于两件事：上下文长度，以及模型在一轮中能准确处理多少条 Trigger。

模拟：Trigger 越密，Router 越“划算”
Router 一次 LLM 请求（数字 = 本轮合并的 Trigger 条数）Trigger 到达
把速率从 1 拖到 40。在“合并很便宜”模型下，平均 batch 变大，单次请求只慢一点，每条 Trigger 分摊的时间明显下降。
再切到“合并不便宜”。同样的速率下，队列越积越长，等待时间失控。批处理省下的，正是这部分。
简化模型：单次请求耗时 = 1.72 秒 + 0.78 秒 × batch（用原文 7.2 的两个端点拟合）；“每条全价”= 2.5 秒 × batch。到达随机，模拟 10 分钟，图中只画前 60 秒。本模型的“分摊”= 单次耗时 ÷ batch，与原文的统计口径不完全相同，只看趋势。

原文据此认为：单个常驻 Router Session 能保持上下文连续，而且在他们目前的团队规模下已经够用。前提是加上订阅与直通、链式召回（见 SA03、SA04）。实验细节见 SA07。

真的不够时：切分

规模再扩大时，单个会话可能确实承载不了。这时 Router 层内部可以设计为多层过滤结构，或水平切分（Sharding）为多个会话。

切分的代价Router 层的内部设计，本质上又回到了连续性与吞吐量的权衡。切分粒度越细，并发吞吐越高，分片之间的记忆与上下文连续性越低。原文说：在全局记忆问题被解决之前，这一权衡始终存在。

05Worker 层：隔离并发

Worker 层由负责具体执行的会话组成。记住四条规则。

  1. 上下文隔离。各个 Worker 彼此隔离，挂载完整的执行工具，在独立上下文里专注完成单一任务。
  2. 配最强的模型。Worker Session 直接决定任务结果与代码质量，通常要配置能力最强的模型。
  3. 不直接对人说话。Worker 的推理过程和工具调用不输出到外部信道。它向 Router 汇报状态，由 Router 统一回复用户。这样既保住并发度和交付质量，又避免多个会话各自回复造成混乱。
  4. 同层不直接通信。各 Worker 独立推进，通常不需要互相通信。
Router 层
轻量模型

交互、分派、全局记忆。不执行具体任务，可以不配 Bash。

Worker 层
最强模型

执行具体任务，挂载完整工具。不直接对人说话。

冲突怎么办

多个 Worker 的冲突，往往出现在同一个 Pull Request 这类共享工作环境里。原文不让 Worker 互相通信。它们只要都订阅了对应的 Thread，就会收到相同的事件通知。所以它们有机会自己发现并解决冲突。少数跨任务协同，由 Router 层中转。订阅机制在 SA03 展开。

Worker 内部也可以有结构

和 Router 一样，Worker 不必局限于单个会话。执行复杂单任务时，Worker 内部可以再创建 Subagent，也可以本身就是一个 Agent Team。这些对上层的 Router 保持透明。

代码协作场景
多线并进

同时推进多个独立的问题复现、PR 评审和特性开发，互不阻塞。

个人助手场景
一个窗口，多个话题

界面上通常只有一个聊天页。你可能在同一对话框里同时聊几个话题。这时前端维持交互连续，底层为每个话题分派一个 Worker。这些 Worker 并行推进任务、起草回复。

06自测与速记

“每个事件都新开一个独立 Session”的方案，主要问题是什么？
这个方案并发吞吐最高。但任务之间并不完全独立。缺少全局上下文，结果会彼此割裂。多个 Session 各自回复，交互会变乱。
关于 Router 层，下面哪一项不符合原文？
需要最强模型的是 Worker 层，因为它直接决定任务结果与代码质量。原文的实践是：Router 的任务没有想象中复杂，较轻量的模型往往就能兼顾速度与效果。
事件密集涌入时，单个 Router Session 仍能撑住，主要靠什么？
这就是批处理。合并后的输入在 Prefill 阶段并行计算。Router 每步是长输入、短输出，多条输入合并后单次耗时增长远慢于批大小。原文实测：batch 从 1.0 升到 2.8，单次请求从 2.5 秒到 3.9 秒，单个决定分摊时间从 6.4 秒降到 1.6 秒。
两个 Worker 在同一个 PR 里改到了同一处代码。按原文的设计，它们一般怎样发现冲突？
同层 Worker 通常不直接通信。只要都订阅了对应的 Thread，就会收到相同的事件，有机会自行发现和解决冲突。少数跨任务协同由 Router 中转。
